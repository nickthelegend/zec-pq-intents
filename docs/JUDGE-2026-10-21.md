# Yaksok (zec-pq-intents): judge and production review, Oct 21, 2026

Reviewed at `535dc73` as a strict hackathon judge (Zecathon, Private Markets) and as a production
reviewer looking for ways to steal the escrow, replay or stretch an intent, or make a check pass on
the wrong input. This was written before any code changed. The "Addressed" section at the end was
added after the fixes.

Grounding run (`535dc73`, Oct 21): `cargo test --release` in `packages/scan` 3 passed + 1 doc test;
protocol 10 passed; node 7 passed (live, Zcash testnet through `testnet.zec.rocks`); mcp 5 passed.
That is 25 tests + 1 doc test, matching TESTING.md.

## Findings (file:line at 535dc73)

### Critical / high

1. **Fill-claim theft: the verifier pays whoever signs a claim.**
   `packages/node/src/verifier.ts:119` only checks that a `FillClaim` is signed by the key it names
   (`verifyFill`, `packages/protocol/src/index.ts:238-243`). Any ML-DSA key will do. The release then
   goes to `claim.solver_ua` (`verifier.ts:130`). The fill txid is not secret: the user sees it in
   their own wallet, and the desk returns it from `GET /api/intents/:hash` (`desk.ts:106`). So the
   user can let the honest solver deliver, then submit a claim for the same fill with their own key
   and address, and collect the delivery plus 45,000 of their 60,000 zat escrow. The node tests
   already show it: `live.test.ts:59-60` signs every claim with a freshly generated "solver" key and
   the verifier accepts that key every time. The docs say the opposite (`packages/docs/README.md:64`:
   the solver "cannot … claim someone else's fill").
2. **Settle and refund race into a double payout.** `admit()` awaits two network calls
   (`verifier.ts:101`, `:124`, `:141`) before `closed[hash]` is set (`:131`, `:146`), and nothing
   serializes decisions. A settle and a refund for the same intent that overlap both pass every
   check, so the escrow pays the solver and refunds the user. `payOnce` (`:62-69`) also checks
   `payouts[key]` before an `await` and stores it after, so two concurrent settles send two releases.
3. **Refund opens one block after the deadline, so the solver can lose a fill it made in time.**
   `verifier.ts:142` refunds as soon as `tip > deadline`. A fill mined at the deadline is valid
   (`:127`), but if the refund lands before the solver's claim is processed (the desk ticks every
   30 s, `serve.ts:67`), the claim is refused `ALREADY_REFUNDED` and the user keeps both the
   delivery and the refund. There is no claim window.
4. **Board squatting.** `Desk.submit` (`desk.ts:43-52`) stores any envelope that carries a 64-hex
   `intent_hash`, without opening it, and keeps the first one per hash. Funding memos `pqi1:<hash>`
   are visible to anyone with the published escrow viewing key, so an observer can post a junk
   envelope under a victim's hash before the victim posts. The victim's real envelope is then ignored
   (`:46-47`), the junk one fails to open and the intent is marked `declined` (`:58-64`). With no
   refund path (finding 6), the escrow stays stuck.
5. **Open, cross-site-reachable admin endpoints and concurrent ticks.** `POST /api/tick` and
   `POST /api/intents` need no auth (`desk.ts:134-138`) and every response says
   `access-control-allow-origin: *` (`:118`). A web page the operator visits can send a plain
   `fetch(…, {method:'POST'})` to `127.0.0.1:8404/api/tick` without a preflight. The interval guard
   (`serve.ts:66-75`) does not cover `/api/tick`, so two ticks run at once: the solver can deliver
   twice (`desk.ts:79-84`) and the verifier sees two settles (finding 2). The request body is read
   with no size limit (`desk.ts:120-124`).
6. **No refund path on the live desk.** `Desk.step` handles `received → funded → filled → settled`
   only (`desk.ts:66-94`). A declined intent (fee too low, deadline too close, unreadable envelope)
   stays `declined` and the escrow stays put. The only refund call in the repo is the example run
   script (`packages/examples/src/run.ts:172`). The MCP `submit_intent` funds the escrow *before* the
   desk has looked at anything (`packages/mcp/src/tools.ts:80-82`).
7. **`verify_log` verifies the desk with the desk's own key.** `tools.ts:102-103` fetches the
   verifier public key from `/api/info` on the same desk whose log it checks, and the anchor viewing
   key too (`:107-111`). A desk that re-signs a different log with a new key gets `ok: true`. The same
   goes for `submit_intent`, which takes the escrow address and the solver's KEM key from the desk
   (`:73-80`) and then pays.

### Medium

8. **Solver accepts intents it cannot fill in time.** `Solver.quote` declines only when
   `tip >= deadline` (`solver.ts:32`). At `tip = deadline - 1` it delivers, the fill is mined after
   the deadline, and the verifier rightly says `EXPIRED`: the solver loses the delivery. That is
   exactly entry #7 of the live run.
9. **1 confirmation.** Every funding and fill check uses `minConf = 1` (`scan.ts:46`,
   `verifier.ts:78`, `:124`). A one-block reorg after a release leaves the escrow paying out of other
   users' deposits.
10. **Crash window in `payOnce`.** The txid is stored after `quicksend` returns (`verifier.ts:66-68`);
    a crash in between pays again on restart. The comment at `:61` says "stored before".
11. **Non-canonical base64.** `fromB64` (`protocol/src/index.ts:33-49`) accepts non-zero padding bits,
    so `"QR=="` and `"QQ=="` decode to the same byte. A signature or key string can be rewritten
    without changing what it verifies. Nothing keys on those strings today, so impact is low, but a
    signed-message system should have one encoding per value.
12. **Anchor equivocation is not detected.** The anchor is a memo to an address the verifier controls,
    and `verify_log` checks only the txid the log names. A verifier could anchor two different heads
    and show each audience one. Catching it means scanning every note the anchor viewing key can see.
    Entries after the last anchor are not covered, and `verify_log` does not say how many there are.
13. **Privacy is weaker than the copy says.** The escrow viewing key is published, so every
    funding's amount, timing and intent hash is public. `receive_uivk` is inside the signed intent
    (`protocol/src/index.ts:121`) and all three live intents use one receive address
    (`examples/src/run.ts:107`), so "fresh address" is not true of the run. The funding and fill
    notes are ECDH-encrypted, and a future quantum adversary that harvests the chain can read their
    memos and link them. ML-KEM protects only the envelope.

### Low

14. Every rejection is signed and logged forever. A caller of `Verifier.settle` can grow the log with
    junk. The desk does not expose `settle` directly, so it is not reachable over HTTP today.
15. The MCP test called "a published desk refuses intents" (`mcp/test/mcp.test.ts:60`) only checks
    the missing agent file.
16. `quote` (`tools.ts:50-57`) is local arithmetic against `min_fee_zat`. It does not ask the solver
    and ignores the deadline, but its description says it "says whether the solver accepts".

## One bold idea

**Make the solver bind itself on-chain.** The fill memo could carry the solver's key id
(`pqi1:<hash>:fill:<solver>`). The release would then be owed to whoever *paid* the fill, as
recorded in the shielded note the user receives, rather than to whoever claims it first, with no
solver registry. Then put the log head into a NEAR testnet contract that runs `ml_dsa_verify`, which
NEAR testnet supports. That would give the verifier's record a public, non-equivocating home that
checks its post-quantum signature on-chain.
